# Рефакторинг (часть 2)

Порядок работы:

1. Перед началом сделан бэкап базы: `pg_dump -Fc online_store -f backups/before_refactoring.dump`. Восстановить его можно командой `pg_restore -c -d online_store backups/before_refactoring.dump`.
2. Изменения вносились небольшими шагами, после каждого прогонялись тесты (`python manage.py test`).
3. Схема базы данных не менялась: `makemigrations --check` не находит изменений, поэтому существующие данные остаются совместимыми.

## Что изменено

| Область | Было | Стало | Зачем |
|---|---|---|---|
| Бизнес-логика | Логика корзины была в методах `Cart.add_item`/`set_quantity`, логика заказа — в представлениях и частично в `services.py` | Вся логика в `store/services.py`: `add_to_cart`, `set_cart_quantity`, `remove_from_cart`, `get_cart_items`, `create_order`, `change_order_status`, `ship_order`, `cancel_order`, `get_sent_orders`, `get_pending_orders` | Функции не зависят от запроса, форм и шаблонов, их можно покрыть unit-тестами и вызывать из админки и команд |
| Проверка остатков | Три разных места: форма, `Cart.add_item` (молча урезал количество), оформление заказа | Одно место в сервисе: при нехватке бросается `InsufficientStockError`, пользователь видит понятную ошибку | Нет дублирования, поведение предсказуемое: нельзя получить в корзине меньше, чем просил, без сообщения об этом |
| Ошибки | `OutOfStockError` в `services.py`, строки и `ValueError` в разных местах | `store/exceptions.py`: `StoreError` → `InsufficientStockError`, `EmptyCartError`, `OrderStatusError` | Представления ловят один базовый класс `StoreError` и показывают его текст |
| Статусы заказа | Статус можно было поменять в админке на любой, при отмене через админку товар не возвращался на склад | Таблица допустимых переходов `STATUS_TRANSITIONS` и функция `change_order_status`; в админке статус меняется только действиями | Нельзя, например, отменить уже доставленный заказ, а отмена всегда возвращает товар на склад |
| Выборки заказов | Фильтры по статусу писались вручную | `OrderQuerySet.sent()` и `.pending()` | Логика «отправлен / не отправлен» описана в одном месте |
| Адрес и ФИО | Поля адреса и форматирование адреса и ФИО дублировались в `Address` и `Order` | Абстрактная модель `AddressFields` и функция `join_full_name` | Нет повторяющегося кода, одинаковый формат адреса везде |
| Представления адресов | `address_add` и `address_edit` — почти одинаковые функции | Одна функция `address_form(request, pk=None)` | Меньше кода |
| Форма заказа | Функция `_checkout_initial` во views | Метод `OrderForm.initial_for(user)` | Логика формы находится в форме |
| Счётчик корзины | Свой запрос в контекст-процессоре, дублирующий `Cart.count` | `services.get_cart_count` | Один источник правды |
| Команда выгрузки | Параметр `format` затенял встроенную функцию, сбор и вывод данных были в одном методе | `dest='fmt'`, функции `collect_residue` и `render_residue` | Функции тестируются отдельно |
| Команда загрузки | Один большой метод `_load` | `_load_categories`, `_load_products`, `_product_fields`, `_copy_image`; флаг `--if-empty` для автозапуска в Docker | Короткие функции проще читать, а повторный старт контейнера не сбрасывает остатки |
| Настройки | Один `settings.py` | `settings/base.py`, `dev.py`, `production.py` | В production `DEBUG=False`, WhiteNoise и обязательный секретный ключ, в разработке удобные значения по умолчанию |
| Магические числа | `12`, `5` прямо в коде | `PRODUCTS_PER_PAGE`, `RECENT_ORDERS_LIMIT` | Понятно, что означает число |
| Тесты | Один `store/tests.py` на 13 тестов | Пакеты `store/tests/` и `users/tests/`, 98 тестов, покрытие 98% | Требование задания и защита от регрессий |

## Чистота кода

- Все модули, классы и функции снабжены докстрингами по PEP 257; проверено `pydocstyle` (D100–D107).
- `flake8` (длина строки 119) и `isort` проходят без замечаний, настройки лежат в `setup.cfg`.
- Отступы везде пробелами: табуляций в `.py`, `.html`, `.css` и `.yml` нет. Файл `.editorconfig` закрепляет это для редакторов.
- Удалены неиспользуемые импорты и переменные, которые находит `flake8` (F401, F841).

## Влияние на приложение

- Для пользователя: при попытке положить в корзину больше, чем есть на складе, теперь выводится ошибка с точным остатком, а количество в корзине не меняется молча.
- Для администратора: статус заказа меняется через «Действия» в списке заказов, прямое редактирование поля статуса отключено.
- Для данных: структура таблиц не изменилась, миграции не нужны.
